SVG Whiteboarding over Shared XML Editing (Minimal Profile)

This specification defines an SVG whiteboard as a Jingle application type whose shared document is synchronized with Shared XML Editing (XEP-0284). It is a minimal, standards-only profile that relies entirely on XMPP Core, Service Discovery, Jingle, Shared XML Editing and Multi-User Chat, and adds only the application type identity and the SVG document conventions. It is intended to replace the deprecated, Psi-specific whiteboarding profile that predated XEP-0284.

1 Introduction

XEP-0113 defines a minimal, message-based whiteboarding protocol built on a restricted subset of SVG path data. It is stateless and does not provide a shared document model.

XEP-0284 (Shared XML Editing, SXE) instead provides a general mechanism for collaboratively editing an XML document: participants synchronize a set of records that map onto a DOM tree, and XEP-0284 defines Jingle as the session management layer for such sessions. A whiteboard is a natural SXE application: the shared XML document is an SVG document.

This specification defines that application type. It is deliberately minimal: it adds no new XML vocabulary beyond one Jingle application-type namespace, and it defines only the conventions needed to interpret the shared SVG document. Everything else — session management, records, edits, conflict handling — is defined by Jingle (XEP-0166) and Shared XML Editing (XEP-0284).

An earlier whiteboarding profile used by the Psi client relied on a pre-standardization (ProtoXEP) form of SXE with a custom negotiation vocabulary and the namespace http://jabber.org/protocol/sxe. That profile is deprecated. This specification is the standards-based replacement, and Psi is expected to be updated to implement it.

2 Requirements

  1. Allow freehand drawing and geometric editing on a shared canvas.
  2. Represent the canvas as a self-describing SVG document.
  3. Use existing standards for session management and synchronization, introducing no new synchronization vocabulary.
  4. Support one-to-one and multi-user whiteboards.
  5. Interoperate across independent implementations.
  6. Require no server modifications beyond those already required by the referenced specifications.

3 Glossary

Shared SVG Document
The SVG document, rooted at <svg/>, that holds the whiteboard contents and is synchronized by SXE.
Whiteboard Session
An SXE session (XEP-0284) whose Jingle application type is urn:xmpp:jingle:apps:svg-whiteboard:0.
Host
The entity that relays SXE payloads; the session initiator, a Multi-User Chat room, or a dedicated component.
Record
The synchronized state of a single DOM node (defined in XEP-0284).
RID
The record identifier (defined in XEP-0284), distinct from the SVG id attribute.
Canvas
The drawing area, defined by the viewBox attribute of the root <svg/> element.

4 Application Format

The whiteboard is identified as a Jingle application type by the namespace urn:xmpp:jingle:apps:svg-whiteboard:0. This namespace is used on the Jingle <description/> element and has no child elements in the minimal profile.

The shared XML document of the session is an SVG document whose root element is <svg/> in the namespace http://www.w3.org/2000/svg. The document conventions are defined in Section 10.

5 Session Management

Session management is provided by Jingle (XEP-0166), as required by XEP-0284. The application supplies the <description/> element, and the transport is the SXE Jingle transport urn:xmpp:jingle:transports:sxe, which carries at least one <host/> element.

A session is ended, or an offer refused, with a Jingle session-terminate. A responder that does not support the application type SHOULD use the unsupported-applications reason.

6 Feature Discovery

An entity that supports this profile MUST advertise, via Service Discovery (XEP-0030), the following features:

  • urn:xmpp:jingle:1 — Jingle is supported.
  • urn:xmpp:sxe:0 — Shared XML Editing is supported.
  • urn:xmpp:jingle:transports:sxe — the SXE Jingle transport is supported.
  • urn:xmpp:jingle:apps:svg-whiteboard:0 — this application type is supported.

It SHOULD also expose the shared-editing identity described in XEP-0284 (discovery identity type sxe in the collaboration category).

7 Connecting and Initial State Synchronization

Once the Jingle session exists, participants use the SXE payload defined in XEP-0284: an <sxe/> element in the namespace urn:xmpp:sxe:0, carried in a <message/>, with REQUIRED session and id attributes.

7.1 Connecting

To join a session, an entity sends an SXE <connect/> element to the host.

7.2 State Offer, Acceptance and Refusal

The host (or the initiator) offers the current document state with <state-offer/>. The offer MUST contain the same <description/> element that was used in the Jingle session-initiate, so that the joiner can verify the application type.

The joiner accepts one offer with <accept-state/> and refuses unwanted offers with <refuse-state/>.

7.3 Sending the State

The state is sent inside a <state/> element bracketed by <document-begin/> and <document-end/>. The prolog attribute of <document-begin/> carries the XML prolog (including the DOCTYPE) as a data: URI.

8 Editing the Whiteboard

All edits are SXE edits inside a <state/> element (XEP-0284). The three edit elements are:

  • <new/> — create a record (attributes rid, type, parent, primary-weight, ns, name, chdata, and optionally version).
  • <set/> — change a record (attributes target, version, and the field or fields being changed, including parent, primary-weight, name, chdata, replacefrom, replacen).
  • <remove/> — remove a record (attribute target).

Ordering among siblings is determined by primary-weight and, on ties, by the secondary weight (RID comparison) as defined in XEP-0284. The following examples use the root RID 0 from Section 7.3.

8.1 Drawing a Path

Freehand drawing creates a <path/> element and its attributes. Every element that can be selected, transformed, reordered, grouped or deleted SHOULD carry a unique id attribute.

Implementations MAY smooth freehand input by emitting SVG curve commands (Q, C) in the d attribute.

8.2 Moving and Transforming an Element

Transformations are represented by the SVG transform attribute. There is no separate move command: moving, rotating or scaling updates the attribute record with a <set/>.

8.3 Changing Style

A partial replacement MAY use replacefrom and replacen.

8.4 Erasing an Element

RIDs of removed records MUST NOT be reused within the session.

8.5 Grouping and Ungrouping

Grouping creates a <g/> element and reparents the selected records under it by changing their parent field.

Ungrouping composes the group's transform into each child, moves the children back to the group's parent, and removes the group.

9 Multi-User Whiteboards

10 Initial Document

When a session is started without a user-supplied document, the initiator MUST initialize it to the empty whiteboard document below.

  • The root element MUST be <svg/> in http://www.w3.org/2000/svg.
  • The canvas MUST be described by the viewBox attribute.
  • SVG Tiny 1.2 (or a compatible profile) SHOULD be used; baseProfile='tiny' is RECOMMENDED.
  • Drawable content consists of SVG elements such as <path/>, <image/>, <g/> and basic shapes.
  • Metadata (<title/>, <desc/>, <defs/>) MUST NOT be treated as drawable items and SHOULD be preserved.

11.3 Grammar of the d Attribute

The d attribute uses the full SVG path data grammar (from the SVG specification); the supported commands include moveto (M/m), lineto (L/l), horizontal and vertical lineto (H/h, V/v), closepath (Z/z), cubic and smooth cubic curves (C/c, S/s), quadratic and smooth quadratic curves (Q/q, T/t), and elliptical arcs (A/a). The transform attribute uses the SVG transform-list grammar.

12 Security Considerations

  • Embedded data: images can be large; implementations SHOULD enforce size and format limits.
  • Clients SHOULD render the shared document without fetching external resources.
  • Any participant may edit the document; access control is out of scope and may be provided by the host.
  • The XML prolog carried in the prolog attribute MUST be treated as untrusted input.
