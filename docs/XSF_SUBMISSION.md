# Подача whiteboard-профиля в XSF

> English version: [`XSF_SUBMISSION.en.md`](XSF_SUBMISSION.en.md)

Как превратить профиль из этого репозитория в XMPP Extension Protocol. Факты о процессе взяты из XEP-0001, XEP-0143 и документации редакторов в репозитории `xsf/xeps` (`docs/PROCESSING.md`, `docs/TRIAGING.md`).

## 1. Что подавать

Работа делится по уровням на две подачи:

1. **Один ProtoXEP «SVG Whiteboarding»** (shortname `svg-whiteboard`, Standards Track, утверждает Council). Он определяет Jingle application type и всё, что относится именно к доскам:
   - сессии один-на-один (Jingle, предложения XEP-0353, права на правку через `senders`);
   - доски в групповых чатах (SXE-сессия, в которой host — комната);
   - правила SVG-документа (корень, namespace, элементы, трансформации, изображения, текст);
   - соображения безопасности и приватности.

   Namespace остаётся `urn:xmpp:jingle:apps:svg-whiteboard:0`, потому что Psi 1.6 уже его использует. В подаче нужно попросить Editor сохранить его.
2. **Ревизия XEP-0284 до 0.2**, с согласия её авторов. В неё входит всё, что касается Shared XML Editing в целом:
   - SXE-сессия = Jingle `sid`;
   - доставка сообщений и подсказки XEP-0334;
   - передача состояния только текущими версиями;
   - поле `ns`;
   - Jingle `senders`;
   - полезная нагрузка по Jingle-соединениям и защищённая полезная нагрузка;
   - уточнения для групповых чатов;
   - настоящие Security Considerations и редакторские исправления.

Всё, что определено в XEP-0284, остаётся там; всё, что относится к SVG, переходит в новый документ. Ни одна подача не обязана ждать другую.

XEP-0284 находится в статусе Experimental (версия 0.1.4). XEP-0113 (Simple Whiteboarding) — Deferred; новый документ может указать, что заменяет XEP-0113.

## 2. Что изменить в черновике до подачи

- **Правовое уведомление:** XEP-0001 требует ровно тех уведомлений, что даёт XSF IPR Policy. Собственный блок `<legal>` заменяется на `&LEGALNOTICE;`. При подаче права на текст переходят к XSF.
- **Авторы:** XEP-0001 требует для каждого автора имя, фамилию, email и JID, поэтому автор-заглушка заменяется настоящими авторами.
- **Один документ:** минимальный и расширенный профили сливаются. Расширенный текст — строгое надмножество минимального, поэтому он и становится документом, а его расширения помечаются как необязательные.
- **Заголовок:** `<number>xxxx</number>`, `<status>ProtoXEP</status>`, shortname `svg-whiteboard`, одна ревизия с версией `0.0.1`. Последние два пункта Editor проверяет перед слиянием.
- **Разделы:** шаблон XEP помечает как обязательные Security Considerations, Privacy Considerations, Accessibility Considerations, IANA Considerations, XMPP Registrar Considerations и XML Schema (для протокольных спецификаций). Business Rules и Implementation Notes — по желанию.
- **Файл:** один файл `inbox/svg-whiteboard.xml`; его имя не должно начинаться с `xep-`.

## 3. Шаги

### До подачи

1. Договориться с мейнтейнером Psi о соавторстве, а с авторами XEP-0284 — о планируемой ревизии. Конкурирующее предложение — худший исход.
2. Собрать подтверждение совместимости. Две независимые реализации (Psi и another.im) должны провести одну и ту же сессию (предложение, передача состояния, правки, завершение), а результат нужно указать в подаче или в рассылке.
3. Каждый автор читает XSF IPR Policy. Подача документа означает согласие с ней.

### ProtoXEP

1. Сделать fork `github.com/xsf/xeps` и создать ветку.
2. Скопировать подготовленный документ в `inbox/svg-whiteboard.xml`. Другие файлы не менять.
3. Проверить и отрендерить документ инструментами самого репозитория (`xmllint`, `xsltproc`):

   ```sh
   xmllint --nonet --noout --noent --loaddtd --valid inbox/svg-whiteboard.xml
   xsltproc --path . --param htmlbase "'../'" xep.xsl inbox/svg-whiteboard.xml > /tmp/svg-whiteboard.html
   ```

4. Сделать один коммит и открыть pull request с заголовком `ProtoXEP: SVG Whiteboarding`.
5. Editor проверяет формат, сливает PR и публикует предложение в `xmpp.org/extensions/inbox/`, затем объявляет о нём в standards@xmpp.org и просит Council принять его. Стоит отправить в standards@ и своё короткое письмо с мотивацией и подтверждением совместимости.
6. В течение 14 дней председатель Council опрашивает членов. Если никто не возражает, Editor присваивает номер, ставит статус Experimental, публикует версию 0.1 и объявляет о ней.
7. Если возражения есть, нужно учесть замечания, доработать предложение и подать его снова (новым PR, обновляющим файл в `inbox/`).

### Ревизия XEP-0284

1. Обсудить изменение в standards@, поставив авторов XEP-0284 в копию.
2. Открыть pull request только к `xep-0284.xml` с заголовком `XEP-0284: …`. Добавить блок ревизии с версией `0.2.0`; содержательное изменение поднимает минорный номер.
3. Поскольку изменение исходит не от авторов, Editor ставит метку «Needs Author» и сливает PR после явного согласия одного из авторов. Если Council сочтёт авторов неотвечающими, он может добавить другого автора.
4. Для Experimental XEP голосование Council не требуется. Содержательная ревизия заново запускает 12-месячный отсчёт, после которого неактивная XEP становится Deferred.

## 4. Порядок

1. Слить здесь открытые PR к профилю.
2. Провести тест совместимости двух реализаций.
3. Внести правки из раздела 2.
4. Получить согласие соавторов.
5. Подать ProtoXEP, а параллельно обсудить ревизию XEP-0284 и открыть PR к ней.
