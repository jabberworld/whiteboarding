Collaborative SVG Whiteboarding over Shared XML Editing

This specification defines an SVG-based collaborative whiteboarding profile that is transported using Shared XML Editing (SXE). It formalizes, at the XMPP protocol level, the whiteboarding model implemented by the Psi instant messaging client: a shared SVG document that participants edit collaboratively and synchronize through SXE records. The specification is intended to be sufficiently detailed that an independent client can interoperate with Psi.

1 Introduction

XEP-0113: Simple Whiteboarding defines a deliberately minimal whiteboarding protocol: a <path/> element carrying a restricted subset of SVG path data, plus <move/> and <delete/> elements, all embedded in <message/> stanzas qualified by the http://jabber.org/protocol/swb namespace. That protocol is stateless and command-oriented: participants exchange incremental commands and never share a document object.

The Psi instant messaging client implements a different, richer whiteboarding model. Instead of exchanging commands, participants share a single SVG document and synchronize the edits (node insertions, moves, attribute and character-data changes, and node removals) through XEP-0284: Shared XML Editing (SXE). The shared XML object is an SVG document rooted at <svg/> in the namespace http://www.w3.org/2000/svg; that same URI is used as the feature that identifies the SVG whiteboard application.

Psi's implementation predates the Jingle-based session management that XEP-0284 later standardized. It negotiates SXE sessions using dedicated <negotiation/> elements inside the <sxe/> payload of <message/> stanzas, under the namespace http://jabber.org/protocol/sxe. This specification documents that Psi-native profile, because it is the profile that a third-party client must implement in order to interoperate with Psi as it exists today. A mapping to the XEP-0284 Jingle-based profile is noted where relevant.

This specification does not attempt to be wire-compatible with XEP-0113. Clients that support both SHOULD advertise the two feature namespaces separately and negotiate the appropriate profile per session.

2 Requirements

The protocol defined herein provides the following functionality:

  1. Freehand drawing and geometric editing on a shared canvas.
  2. A shared, self-describing document (SVG) that any participant can edit.
  3. Support for one-to-one sessions and for multi-user sessions hosted in a Multi-User Chat room or similar host.
  4. Synchronization of concurrent edits without a mandatory central server.
  5. Reuse of an existing collaborative XML editing protocol rather than defining a new command set.
  6. No server modifications beyond what XMPP Core, Service Discovery, Multi-User Chat and Shared XML Editing already require.
  7. Independence from any particular GUI toolkit or implementation language.

3 Glossary

Shared SVG Document
A single SVG document, rooted at <svg/>, that represents the whiteboard contents and is kept synchronized among all participants.
Whiteboard Session
A negotiated SXE session whose shared XML document is an SVG document and whose negotiated feature list includes http://www.w3.org/2000/svg.
Host
The JID to which SXE messages are sent for relaying to the other participants; this can be the initiator (one-to-one) or a Multi-User Chat room or a specialized editing component.
GUID
A globally unique identifier used as the session identifier (the <sxe/> 'session' attribute).
Record
The state of a single DOM node of the shared document, identified by a Record ID (RID). A record stores fields such as the node type, parent, name, namespace, character data and primary weight.
RID
The Record ID: a GUID assigned to a record when it is created. A RID is distinct from the SVG id attribute of an element.
Edit
A single SXE element (<new/>, <set/> or <remove/>) that creates, changes or removes a record.
primary-weight
A number attached to each record that determines the ordering of a node among its siblings. Higher weight renders later (on top).
secondary weight
The tie-breaker used when two sibling records have equal primary weight: the RIDs are compared character by character by Unicode value; the greater RID has greater weight.
Canvas
The drawing area of the whiteboard, defined by the viewBox attribute of the root <svg/> element.

4 Feature Discovery

Support for this profile is advertised through XEP-0030: Service Discovery. An entity that supports collaborative SVG whiteboarding MUST advertise both of the following features in its service discovery information:

  • http://jabber.org/protocol/sxe — the entity supports Shared XML Editing.
  • http://www.w3.org/2000/svg — the entity supports the SVG whiteboard application type.

An initiating entity MUST NOT start a whiteboard session unless the peer advertises both features. This requirement follows directly from Psi's capability check, which verifies the SXE namespace together with the requested application features.

5 Session Negotiation

All SXE payloads are carried in <message/> stanzas. Each payload is a <sxe/> element qualified by the namespace http://jabber.org/protocol/sxe. The <sxe/> element carries two REQUIRED attributes, described in Section 9.1: session (the session GUID) and id (a per-sender unique identifier for that payload). Negotiation messages additionally contain a <negotiation/> child; a message MUST NOT mix <negotiation/> with ordinary edits.

5.1 Initiating a Session

To start a whiteboard session, the initiator generates a session GUID, creates the initial Shared SVG Document (see Section 8), and sends an <invitation/> listing the required application features. The feature list MUST include http://www.w3.org/2000/svg.

In a multi-user context the same stanza is sent with type='groupchat' to the bare room JID (see Section 7).

5.2 Accepting an Invitation

A receiver of an <invitation/> whose feature list contains a feature it supports accepts the invitation by returning <accept-invitation/> to the inviter.

5.3 Declining an Invitation

If the receiver does not support the offered application features, or the user declines, it returns <decline-invitation/>. When the receiver already participates in a session with the initiator and prefers that session, it MAY include one or more <alternative-session/> children naming the existing session GUID.

Either party MAY abandon an in-progress negotiation with <abort-negotiation/>. If the session has not yet been established, this deletes the pending session; if it has been established, the negotiation is torn down but the session remains.

5.4 Joining an Existing Session

A participant that learns of an existing session (for example from presence advertising or from a MUC room) joins it by sending <connect-request/> to the host.

In a one-to-one session the initiator MUST offer the document state by replying with <history-offer/>. In a multi-user session both the host and the initiator MUST offer the state, and other participants MAY offer it; the joiner SHOULD prefer an offer from the host or initiator.

The joiner accepts one offer with <accept-history/> and MUST ignore edits received before it has chosen an offer. Offers not chosen SHOULD be refused with <refuse-history/>.

5.5 Transferring the Document State

The state is transferred as a sequence of edits bracketed by <document-begin/> and <document-end/>, all inside the <negotiation/> element:

  1. The sender emits <document-begin/> and simultaneously snapshots the document. Its prolog attribute carries the XML prolog (including the DOCTYPE) as a data: URI (RFC 2397). In a one-to-one session the sender MAY also set available-uuid-prefix to reserve a RID prefix for the receiver.
  2. The sender emits the snapshot as a sequence of <new/> edits, optionally followed by the <set/> edits that have occurred since version 0.
  3. The sender emits <document-end/>. Its used-sxe-ids attribute is a semicolon-separated list of the <sxe/> payload IDs already seen by the sender.

While the state is being sent, the sender MUST NOT send any other edits. The receiver MUST NOT apply incoming edits until <document-end/> has been processed.

5.6 Ending a Session

When an entity leaves an established session it MUST notify the other participants with <left-session/> so that the remaining participants can update their user interfaces. The shared document itself is not modified by this notification.

6 Editing the Whiteboard

Once a participant has received the initial state it edits the shared SVG document by sending edits. Every edit is a child of an <sxe/> element (with <negotiation/> absent) and MAY be batched: a single <sxe/> payload can contain any number of <new/>, <set/> and <remove/> elements.

This section describes, for each whiteboard operation, the SVG DOM mutation it performs and the corresponding SXE edits. The examples use short, readable RIDs; real implementations use GUIDs. RID 0 is the root <svg/> element introduced in Section 5.5.

6.1 Drawing a Path

Freehand drawing creates a new <path/> element, its d attribute holding the path data, and presentation attributes such as stroke and stroke-width. Every element that can later be selected, transformed, reordered, grouped or deleted MUST also carry an id attribute that is unique within the document; the implementation generates it with an application prefix (Psi uses e followed by a UUID).

Implementations MAY smooth freehand input by emitting quadratic or cubic curve commands (Q, C) in the d attribute rather than a dense sequence of line commands. Psi, for example, emits quadratic curves. The path data grammar is recalled in Section 9.8.

6.2 Moving and Transforming an Element

Geometric transformations are represented by the SVG transform attribute. There is no separate "move" command. Translating, rotating or scaling a selection updates the transform attribute of the affected element (or group) with a new value, carried as a <set/> edit on that attribute's record. Because the attribute record already exists, the edit uses its RID and the next version number.

6.4 Erasing an Element

Erasing removes the element from the document with one or more <remove/> edits. Removing an element also removes its attribute and descendant records; an implementation MAY emit a <remove/> for each record or rely on the removal of the subtree. A <remove/> may target any record type (element, attribute, text, comment or processing instruction).

After a record has been removed its RID MUST NOT be reused within the session.

6.5 Grouping Elements

Grouping two or more selected elements creates a new <g/> element and reparents the selected element records under it. The group is created with a primary-weight that places it at the stacking position of the topmost grouped element, and each selected element's parent field is changed to the group's RID.

6.6 Ungrouping Elements

Ungrouping moves each child of a <g/> back to the group's parent (or to the root), preserving the stacking order, composes the group's transform into each child's transform, and removes the group. Composition is required so that the visual result is unchanged.

6.7 Changing the Stacking Order

Stacking order is determined by the records' primary-weight values among siblings (higher weight is drawn later, i.e. on top). Bringing an element forward sets its primary-weight above that of the element it should pass; sending it backward sets it below.

Because ordering is also affected by the secondary weight (the RID comparison) when primary weights are equal, implementations SHOULD choose primary-weight values that leave room for later insertions, for example by using fractional weights such as 3.5 to place an element between weights 3 and 4.

6.8 Inserting an Image

Inserting an image creates an <image/> element with the SVG positioning attributes x, y, width and height, and an xlink:href attribute. To keep the shared document self-contained, the image data SHOULD be embedded as a data: URI. The XLink namespace is http://www.w3.org/1999/xlink.

6.9 Resizing the Canvas

The canvas geometry is controlled by the viewBox attribute of the root <svg/> element. Resizing the canvas is a <set/> edit on that attribute's record (RID 3 in the initial state).

6.10 Clearing the Canvas

There is no dedicated clear command. Clearing the whiteboard removes every drawable child element of the root <svg/>. Non-drawable metadata such as <title/>, <desc/> and <defs/> SHOULD be preserved.

7 Multi-User Whiteboards

A whiteboard can be hosted in a Multi-User Chat room (or a specialized component). The host is the room's bare JID; SXE payloads are sent as type='groupchat' messages to that JID and are reflected by the room to all occupants. The application feature and the SXE namespace are discovered from the room's service discovery information.

Broadcast presence within the room MAY advertise the session using an <sxe/> element carrying the session GUID and an optional descriptive name:

Notice of a participant leaving is the same <left-session/> payload defined in Section 5.6. Because every occupant receives every edit, a room-based session permits more than two simultaneous editors without any additional protocol.

8 Initial Document

When a session is started without a user-supplied document, the initiator MUST initialize it to the empty whiteboard document shown below. The document is an SVG document whose root is <svg/> in the namespace http://www.w3.org/2000/svg, whose canvas is defined by viewBox, and which carries the SVG 1.1 Tiny profile marker baseProfile='tiny'.

  • The root element MUST be <svg/> in http://www.w3.org/2000/svg.
  • The canvas MUST be described by the viewBox attribute.
  • The SVG 1.1 Tiny (or a compatible) profile is RECOMMENDED.
  • An initiator MAY use a user-supplied SVG document as the initial document; the same constraints apply to it.
  • Metadata elements (<title/>, <desc/>, <defs/>) MUST NOT be treated as drawable whiteboard items and SHOULD be preserved.

9.4 Mapping Records to the SVG DOM

Whenever a record is added, changed or removed, each client MUST ensure that the DOM node corresponding to each record satisfies the following:

  1. The parent of each node MUST be the node of the record named by its parent field. If that record does not exist, the node MUST be removed. An empty parent means the node is a child of the document itself.
  2. Each node MUST be placed after the sibling node with the greatest weight less than its own weight, where weight is ordered first by primary-weight and then by the secondary weight (RID comparison).
  3. The namespace and name of each element and attribute MUST equal the corresponding record fields.
  4. The value of each attribute and the content of each text or comment node MUST equal the record's chdata.
  5. The target and data of each processing instruction MUST equal pitarget and pidata.
  6. The document MUST remain well-formed and SHOULD remain valid against the schema in Section 9.6.

9.5 Commutative and Non-Commutative Edits

Edits that add or remove records are commutative: they can be applied in any order and need not be retained for history. Edits that change an existing record (<set/>) are non-commutative: concurrent changes to the same record may conflict, so a history of such edits is REQUIRED.

  • Without a server component, every client MUST retain all non-commutative edits that have not been undone and whose records have not been removed.
  • With a server component, the server MUST retain all non-commutative edits and resolve out-of-order edits before relaying them; a client need only retain its own non-commutative edits until it receives a competing edit to the same record from another entity.

9.8 Grammar of the d Attribute

Unlike XEP-0113, this profile permits the full SVG path data grammar, so that freehand strokes can use curve commands. The relevant subset (from the SVG specification) is recalled below. 

path-data:
    wsp* moveto-drawto-command-groups? wsp*

moveto-drawto-command-groups:
    moveto-drawto-command-group
    | moveto-drawto-command-group wsp* moveto-drawto-command-groups

moveto-drawto-command-group:
    moveto wsp* drawto-commands?

drawto-commands:
    drawto-command
    | drawto-command wsp* drawto-commands

drawto-command:
    closepath | lineto | horizontal-lineto | vertical-lineto
    | curveto | smooth-curveto | quadratic-bezier-curveto
    | smooth-quadratic-bezier-curveto | elliptical-arc

moveto:
    ( "M" | "m" ) wsp* moveto-argument-sequence

closepath:
    ( "Z" | "z" )

lineto:
    ( "L" | "l" ) wsp* lineto-argument-sequence

horizontal-lineto:
    ( "H" | "h" ) wsp* horizontal-lineto-argument-sequence

vertical-lineto:
    ( "V" | "v" ) wsp* vertical-lineto-argument-sequence

curveto:
    ( "C" | "c" ) wsp* curveto-argument-sequence

smooth-curveto:
    ( "S" | "s" ) wsp* smooth-curveto-argument-sequence

quadratic-bezier-curveto:
    ( "Q" | "q" ) wsp* quadratic-bezier-curveto-argument-sequence

smooth-quadratic-bezier-curveto:
    ( "T" | "t" ) wsp* smooth-quadratic-bezier-curveto-argument-sequence

elliptical-arc:
    ( "A" | "a" ) wsp* elliptical-arc-argument-sequence

coordinate-pair:
    coordinate comma-wsp? coordinate

coordinate:
    number

number:
    sign? integer-constant
    | sign? floating-point-constant

comma-wsp:
    (wsp+ comma? wsp*) | (comma wsp*)

comma: ","
sign: "+" | "-"
wsp: (#x20 | #x9 | #xD | #xA)

The transform attribute uses the SVG transform-list grammar; a composed transformation is canonically serialized as a single matrix(a b c d e f).

10 Implementation Notes

10.1 The GUI

This specification does not mandate a user interface. A typical client offers a set of editing modes (select, translate, rotate, scale, scroll, erase, draw path, insert image), controls for stroke colour, fill colour and stroke width, and actions to save the document, change the canvas geometry and end the session. Selection state is local presentation state and MUST NOT be stored in the shared document.

10.2 Element Identity: RID versus id

Two identifiers are involved. The RID identifies an SXE record (a DOM node) and is used by all edit elements. The SVG id attribute identifies an element to the application (for example, as the handle used by a rendering library). Both are REQUIRED for drawable elements; the RID is assigned by SXE, the id attribute is an ordinary attribute record. An element that lacks an id attribute at the moment it becomes part of the shared document SHOULD be given one, and the corresponding <new/> edit for the attribute SHOULD be sent before the element is exposed for individual operations.

10.3 Primary Weight and Stacking Order

primary-weight values need only be ordered, not consecutive. Inserting an element between two existing siblings is done by choosing a weight strictly between theirs; repeatedly doing so can exhaust floating-point precision, so implementations MAY periodically renormalize the weights of a sibling set and emit the resulting <set/> edits.

10.4 Bandwidth and Karma

Drawing produces data quickly, which stresses servers that apply karma limits. Implementations SHOULD: coalesce high-frequency edits into fewer <sxe/> payloads; avoid recording every pointer movement when the position can be interpolated; and prefer relative path commands where they are shorter. Embedded images are potentially large and SHOULD be subject to local size limits.

10.5 Text

The profile has no dedicated text element, because <text/> would substantially increase the required rendering subset. Text MAY be represented as paths, for example by converting glyphs from a stroke font (a Hershey font) into <path/> elements. This keeps text interoperable with every participant and consistent with the freehand model, at the cost of being non-selectable as text.

10.6 Images

Embedding image data as a data: URI keeps the document self-contained but increases its size by roughly one third (base64). An implementation MAY alternatively reference external resources, but doing so makes the shared document dependent on the availability of those resources for every participant and is therefore NOT RECOMMENDED.

10.7 Clearing the Screen

Because there is no clear command, clearing is expressed as a series of <remove/> edits, one per drawable child. Clients that need a finer-grained notion of "clear" (for example, clearing only elements drawn before a certain time) SHOULD implement it locally and MUST NOT introduce non-standard commands into the shared document.

12 Security Considerations

  • Embedded image data can be large; implementations SHOULD enforce size and format limits to avoid resource exhaustion.
  • The shared document is SVG; clients SHOULD render it in a context that does not fetch external resources referenced by the document.
  • Any participant may edit the document; access control and moderation are outside the scope of this specification and may be provided by the host.
  • The XML prolog carried in the prolog attribute MUST be treated as untrusted input and parsed defensively.
