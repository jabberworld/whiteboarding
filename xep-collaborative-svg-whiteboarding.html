Collaborative SVG Whiteboarding

This specification defines a session-based collaborative whiteboarding protocol that uses an SVG document as the shared canvas. It is designed to be functionally compatible with the whiteboarding model used by the Psi Jabber client, while being described explicitly at the XMPP protocol level.

1. Introduction

XEP-0113 ("Simple Whiteboarding") defines a minimal, message-based whiteboarding protocol. While simple, it does not provide a shared document model suitable for richer collaborative editing operations.

The Psi Jabber client implements a session-based collaborative whiteboarding model where participants share a single SVG DOM document synchronized in real time. This specification formalizes that model at the XMPP protocol level.

2. Requirements

3. Terminology

Shared SVG Document: A single SVG DOM tree (root <svg>) representing whiteboard state, synchronized across participants.

Whiteboard Session: A negotiated collaborative session for editing the Shared SVG Document.

Collaborative XML Editing: Mechanism to synchronize DOM mutations (e.g. XEP-0214).

Whiteboard Element: SVG element representing drawable content (<path>, <image>, <g>).

Canvas: Drawing area defined by <svg> viewBox.

4. Feature Discovery

Entities supporting this profile MUST advertise the feature http://www.w3.org/2000/svg via Service Discovery (XEP-0030). This feature URI serves as the capability marker for SVG-based collaborative whiteboarding (consistent with the Psi implementation).

7. SVG Conventions and Constraints

Prefer SVG presentation attributes: stroke, stroke-width, stroke-linecap, stroke-linejoin, stroke-miterlimit, fill, fill-opacity, stroke-opacity, opacity.

Z-order determined by DOM document order; later elements render on top. Reordering operations MUST be expressed as DOM node moves.

  • SVG: http://www.w3.org/2000/svg (REQUIRED).
  • XLink (for <image>): http://www.w3.org/1999/xlink when xlink:href used.
  • <path>: path data MAY include M/m,L/l,Q/q,C/c for smooth strokes.
  • <image>: SHOULD use data URI data:image/<type>;base64,<data> with x,y,width,height.
  • <g>: grouping, MAY have transform.
  • Other SVG elements MAY appear and SHOULD be preserved if unknown.
  • Every selectable/transformable/reorderable/groupable/deletable whiteboard element MUST have unique id attribute.
  • id MUST be unique within document.
  • If missing, generating implementation MUST assign unique id before synchronizing.
  • RECOMMENDED: prefixed UUID (e.g. e + UUID).
  • Removed element IDs SHOULD NOT be reused to avoid ambiguity.
  • Transformations expressed via SVG transform attribute (prefer matrix(...) for composed edits).
  • Interactive transforms update transform (no separate move command).
  • Ungrouping MUST compose group transform into child transforms before removing group.
  • Group creates <g id="..."> (optional transform), inserts at appropriate position, moves selected nodes into group.
  • Ungroup moves children out (preserving stacking), composes group transform into children, removes group.

9. Security Considerations

  • Large embedded images: implementations MAY impose size/format limits.
  • SVG rendering: sandbox RECOMMENDED; avoid fetching external resources (prefer data URIs).
  • Coalescing of high-frequency edits RECOMMENDED to manage bandwidth.
